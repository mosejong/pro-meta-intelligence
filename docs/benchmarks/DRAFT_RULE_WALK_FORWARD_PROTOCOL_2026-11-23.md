# 밴픽 자동 상대 정확도 평가 기준 (주간 재생) · 2026-11-23

**이 문서는 실제 자료로 한 번도 실행하기 전에 고정했다.** 이후 규칙 개선(밴 규칙·픽 순위)은 모두 이 기준으로만 채택 여부를 판단한다. 기준을 바꾸려면 새 날짜의 문서를 만들고, 이 문서의 결과는 그대로 남긴다.

## 왜 새 기준이 필요한가

- 기존 평가는 "경기 전에 따로 내려받은 원본"이 있어야 그 경기를 채점했다(`draft_dataset.py`). 2026 시즌 원본 내려받기는 6~7번뿐이라 9월 평가는 32경기, 11월 진단은 9경기만 채점했다.
- 9월 평가 당시 2026 경기 8,233개 중 첫 세트 약 3,750개가 있었고, 그중 3,486개가 "이전 원본 없음"으로만 빠졌다([9월 기록](draft-season-coverage-2026-09-21.json)).
- 9경기·32경기로는 규칙을 고쳐도 좋아졌는지 판단할 수 없고, 그 경기에 맞추는 과적합 위험이 크다.

## 방식

| 항목 | 고정값 |
|---|---|
| 평가 대상 | 서비스에서 쓰는 `suggestSoloDraftTurn`·`explainSoloDraftTurn` 그대로. 평가 도구 안에서 규칙을 바꾸지 않는다 |
| 원본 | 암호화 보관본 하나에서 가장 최근의 2026 시즌 파일 1개(실행 기록에 해시 고정). 새로 내려받지 않는다 |
| 알려진 시점 | **모의**: 각 경기 행은 경기 후 24시간부터 알려진 것으로 본다 |
| 주간 기준 | 대상 경기가 속한 주의 월요일 00:00 UTC. 그 시점보다 24시간 이전에 끝난 경기만 근거로 쓴다 |
| 근거 범위 | 대상 경기와 같은 패치. 양 팀 모두 그 패치 근거가 있어야 채점한다(기존 기준과 같음) |
| 경기 | 확인된 첫 세트, 표준 20차례 전부. 피어리스 이후 세트는 제외 |
| 입력 | 그 차례 이전 선택만. 실제 선택은 채점에만 쓴다. 시즌 선수 기록은 넣지 않는다 |
| 후보 수 | 3개 고정 |

**한계 (모든 결과에 표시):** 하나의 최신 원본으로 과거를 재생하므로, 나중에 고쳐진 기록이 과거 시점에 보인다. 실제 운영 시스템이 그때 알았던 정보와 같지 않다(`SIMULATED_AVAILABILITY_NOT_LIVE_HISTORY`). 그래서 이 평가는 규칙 개발과 비교용이다. 실전 성능 주장은 아래 최종 확인을 거친다.

## 기간 나누기 (대상 경기 시각 기준, UTC)

| 구분 | 기간 | 용도 |
|---|---|---|
| DEV | 2026-01-01 ~ 06-30 | 규칙을 고치며 자유롭게 확인 |
| VALIDATION | 2026-07-01 ~ 08-31 | 채택 판단. 개선안마다 확인한다 |
| HOLDOUT | 2026-09-01 ~ | **봉인.** 최종 개선안을 정한 뒤 한 번만 연다 |

- HOLDOUT은 평가 도구와 워크플로가 기본으로 재생하지 않는다(`unseal_holdout=false`). 열 때는 결정한 개선안과 함께 한 번 열고, 결과가 나빠도 그대로 기록한다.
- HOLDOUT 일부는 이미 다른 연구에서 봤다: 9월 1~15일(이전 v2 모델 9월 평가), 11월 4~11일(현재 규칙 9경기 진단). HOLDOUT 결과는 전체와 "이전에 보지 않은 경기만"을 함께 보고한다.
- 11월 18일 이후 새 원본이 들어오면, 그 이후 경기는 **실제 시점** 확인용으로 따로 쓴다.

## 측정

- 주지표: VALIDATION의 **top-3 포함률**(실제 선택이 후보 3개 안에 든 비율, 기권 포함 전체 차례 기준).
- 보조: top-1, MRR@3, 기권, 불법 후보(이미 선택됐거나 없는 챔피언), 밴/픽별, 페이즈별, 리그별(30경기 이상 리그만 따로, 나머지는 묶음), 팀 평균(40차례 이상 팀의 top-3 평균).
- 비교 기준선 2개(고정, 조정하지 않음):
  - `BASELINE_PATCH_PRESENCE`: 같은 패치에서 많이 픽·밴된 순서. 밴은 픽+밴 합계, 픽은 픽 수 기준.
  - `BASELINE_TEAM_PRIORITY`: 픽은 자기 팀, 밴은 상대 팀의 자주 쓰는 픽 순서. 부족하면 패치 순서로 채운다.
- 불확실성: 경기 단위로 다시 뽑는 bootstrap 1,000회(seed 20261123)의 95% 구간. 한 경기의 20차례는 서로 연관돼 있어 차례 단위로 독립 취급하지 않는다.

## 개선안 채택 규칙 (2·3단계에 적용)

다음을 **모두** 만족해야 서비스 규칙으로 채택한다.

1. VALIDATION top-3가 현재 규칙보다 높고, 현재 규칙 대비 차이의 95% 구간이 0을 넘는다(같은 경기로 짝지어 비교).
2. VALIDATION의 밴과 픽 각각 top-3가 1%p 넘게 떨어지지 않는다.
3. 따로 보고되는 리그(30경기 이상) 중 어느 리그도 top-3가 3%p 넘게 떨어지지 않는다.
4. 불법 후보 0개, 기권이 늘지 않는다.
5. 최종안은 HOLDOUT을 한 번 열어 결과를 그대로 기록한다. HOLDOUT에서 현재 규칙보다 나쁘면 채택하지 않는다.

이 평가는 **프로 선수의 실제 선택과 얼마나 겹치는지**를 잰다. 더 좋은 밴픽인지, 승률이 오르는지는 재지 않는다.

## 실행

- 워크플로 `Draft rule walk-forward evaluation`(`.github/workflows/draft-walk-forward.yml`)을 수동 실행한다. 암호화 보관본을 실행기 안에서만 풀고, 원본 행과 경기별 입력은 밖으로 내보내지 않는다. 공급처에 새 요청을 보내지 않는다.
- 결과는 집계만 남는다(팀 ID·경기별 기록 없음): 실행 로그의 `WALK_FORWARD_RESULT_BEGIN/END` 사이와 `draft-walk-forward-summary-<run>` 아티팩트. 실행 번호·소스 커밋·보관본 ID·원본 해시를 결과에 함께 적는다.
- 코드: `src/pro_meta_intelligence/backtest/walk_forward_dataset.py`, `web/tests/draft-walk-forward-lib.mjs`, `ops/draft-walk-forward.mjs`. 검사: `tests/test_walk_forward_dataset.py`, `web/tests/draft-walk-forward.test.mjs`.
