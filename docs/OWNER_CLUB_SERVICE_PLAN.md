빠른 시작은 `클럽/팀 선택 → 선수 배정 → 밴픽 → 비교 → 공유`다. 코치 상세, 시즌·출처, 가정 수치, 파일 도구는 필요할 때 펼친다. 가입이나 JSON 편집을 첫 이용 조건으로 만들지 않는다.

**공유 링크는 저장된 선택을 전달하는 스냅샷이고, 실시간 방은 서버가 확정 상태를 동기화한다.** 현재 방 v1은 팀·밴픽만 공유하며 로스터·역할·시즌 카드·개인 분석까지 동기화하지 않는다. 후속 계약과 실제 확인 전에는 공유 범위를 넓혀 표시하지 않는다. 서버 미설정 상태에서는 링크 공유로 안내한다.

## 최소 데이터 계약

| 객체 | 최소 필드와 제약 |
|---|---|
| Owner | `ownerId`: 내부 UUID. 게스트는 로컬 임시 소유 상태이며 제공자 계정을 가장하지 않는다. |
| ExternalIdentity | `ownerId`, `provider`, `issuer`, `subject`; `(issuer, subject)` UNIQUE. 서버가 검증한 제공자 사용자 ID를 subject로 정규화한다. OAuth 사용자 ID와 OIDC의 검증된 `iss/sub`를 혼동하지 않는다. 표시명·이메일은 소유권 키가 아니다. |
| Club | `clubId`: UUID, `ownerId` 또는 게스트 로컬 참조, `name`, `revision`, `schemaVersion`. 서버 저장 시 owner 권한을 매 요청 확인한다. |
| ClubSeat | `clubId`, `seatId`, `seatType: coach/scout`, `occupantId?`. 코치 좌석은 `head/assistant`를 구분한다. 직책 선택은 실제 직원 계약이나 서비스 접근 권한 부여가 아니다. |
| RosterSlot | `clubId`, `role: TOP/JUNGLE/MID/BOTTOM/SUPPORT`, `playerId`, `source`, `season`, `status: virtual/observed`. 다섯 역할의 선수 ID를 저장하고 출처별 ID로 식별한다. |
| CoachSelection / Scenario | 코치 ID·출처·시즌·관측/가상 상태, 로스터·좌석 참조, 패치·자료/규칙 버전·시드·명시적 가정. 사용자 배정은 가상이며 관측 경력을 공식 현직으로 승격하지 않는다. |

코치·스카우트는 선택·역할 정보부터 제공한다. 이름·명성·우승 경력에서 코치 능력치나 팀 승률 보너스를 추론하지 않는다. 선수 시즌 간 실력·시너지·현 패치 적응력도 관측 기록만으로 생성하지 않는다.

## 계정 연결과 OAuth 후속 조건

계정 연결은 로그인한 기존 소유자의 재인증과 연결할 제공자 계정의 새 인증, 명시적 연결 확인을 요구한다. 이름·이메일이 같아도 자동 합치지 않는다. 이미 다른 owner에 연결된 identity는 거부하고 원본 클럽을 보존한다. 게스트 저장은 가져올 클럽 미리보기와 충돌 선택 후 귀속하며, 인증 성공만으로 덮어쓰지 않는다.

2026-11-18 공식 페이지 열람 기준의 후속 설계이며, 앱 등록·설정·필요 심사 조건은 **대기/미검증**이다. 실제 로그인 활성화·성공을 주장하지 않는다.

- 두 제공자는 서버의 authorization code 교환과 요청별 일회성 `state` 검증을 기본으로 한다. client secret은 서버에만 보관하고 프런트 빌드에 넣지 않는다. access/refresh token은 URL·공유 링크·내보내기·로그에 넣지 않으며 서버 세션은 Secure/HttpOnly 쿠키로 관리한다. 인가 코드는 콜백에서 즉시 교환하고 제거한다. [카카오 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [Discord OAuth2 공식 문서](https://github.com/discord/discord-api-docs/blob/main/developers/topics/oauth2.mdx)
- PKCE는 공식 지원이 확인된 흐름에 적용한다. 카카오 REST 문서는 S256 지원을 명시하고 Discord 문서는 운영용 code+PKCE를 권고한다. 실제 사용 흐름의 challenge/verifier 파라미터와 실패 처리를 구현 단계에서 대조·검증하며 문서 열람을 인증 검증으로 간주하지 않는다. [카카오 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [Discord OAuth2 공식 문서](https://github.com/discord/discord-api-docs/blob/main/developers/topics/oauth2.mdx)
- Discord는 `identify`만 기본 요청하고 이메일·길드·봇 권한은 추가하지 않는다. 카카오는 이메일·연락처 등 추가 동의항목을 기본 요청하지 않는다. [Discord 범위·코드 흐름](https://github.com/discord/discord-api-docs/blob/main/developers/topics/oauth2.mdx), [카카오 로그인 이해하기](https://developers.kakao.com/docs/ko/kakaologin/common)
- 공개 전 앱 소유·등록, 카카오 로그인 사용 설정, 정확한 redirect URI와 secret 구성, 실제 동의항목 및 제공자별 공개/가입·심사 요구를 확인한다. 현재 저장소의 설정 완료로 해석하지 않는다. [카카오 사전 설정](https://developers.kakao.com/docs/en/kakaologin/prerequisite), [Discord OAuth2 설정·교환](https://github.com/discord/discord-api-docs/blob/main/developers/topics/oauth2.mdx)

## 바로 다음 구현과 실제 한계

1. 부모가 진행 중인 방 v1의 계약별 결과를 먼저 기록한다. 임시 메모리 방은 재시작 시 사라진다. **로컬에서 검사한 방 v1도 배포되거나 안정적인 운영 호스팅이 확보됐다는 뜻은 아니다.**
2. 다음 배치는 게스트 클럽·코치 좌석·5역할 로스터의 로컬 편집/저장 계약이다. 이후 시즌 카드 → 근거/빌드 → 제한된 가정 엔진 순서로 입력과 증거를 연결한다.
3. 역사 자료는 현재 문서상 2022·2026 원본이 있고 나머지는 미수집이다. 2014~현재 파일 목록 등록을 전체 카드 검증 완료로 표현하지 않는다. 기존 제공자 요청 간격·권한·해시 검증을 유지한다.
4. **클라우드 클럽 저장과 운영용 실시간 방에는 영속 백엔드가 필요하다.** DB, 소유권·세션, 방 복구·만료, 연결 관리·남용 제한·운영 관측을 갖추고 검증한다. 정적 사이트나 로그인 버튼만으로 이 관문을 충족하지 못한다.
5. 공개 OAuth 직전에만 사용자 결정이 필요한 항목을 모은다: 운영/콜백 도메인, 영속 백엔드 제공자, 필요한 서비스 가입·앱 등록 주체와 실행 승인. 그 전에는 선택 가능한 계약과 게스트 기능을 진행한다. 이 문서 작성으로 가입·키 설정·구매·배포를 실행하지 않는다.

이 작업은 문서만 작성하며 코드·설정·키·다른 문서 변경, 에이전트 실행, 테스트·배포를 포함하지 않는다. 위 검사 항목은 후속 구현의 완료 조건이다.
